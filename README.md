# Darviq-Observability

Automated monitoring for cloud workloads, entirely as code: **Prometheus** collects metrics,
**Grafana** shows them on dashboards that are generated from code, **Alertmanager** routes alerts,
and exporters watch the applications, the host, every container, and public websites from the
outside. Alert rules have unit tests, every alert links to a runbook, and CI checks all of it on
every change.

It runs against real things: the 11 services of [Darviq-Buzz](https://github.com/ravishekharg/Darviq-Buzz),
the Docker host and its containers, and [darviq.com](https://darviq.com) (uptime and TLS
certificate). In its first hour it caught a real bug, a misconfiguration of my own, and a latency
problem; see [What it found](#what-it-found).

## What's in it

| Piece | What it does |
|---|---|
| **Prometheus** (`prometheus/`) | Scrapes every 15 s. Targets come from JSON files: adding a product to monitoring means dropping a file in `targets/apps/` or `targets/probes/`, picked up within a minute with no restart. |
| **Recording rules** (`rules/recording.yml`) | Request rate, error ratio, p95 latency, disk/CPU/memory ratios computed once, so a dashboard panel and the alert that pages someone always agree. |
| **Alert rules** (`rules/alerts.yml`) | 13 alerts across availability, services, capacity and the monitoring pipeline itself. |
| **Rule unit tests** (`tests/alerts_test.yml`) | 10 `promtool` tests feed synthetic metrics in and check exactly which alerts fire, including the look-alike cases that must *not* page anyone. |
| **Alertmanager** (`alertmanager/`) | Groups by alert and product (one outage = one notification, not eleven), repeats critical alerts hourly, suppresses symptom alerts while a whole product is down. |
| **On-call receiver** (`alert-receiver/`) | A small webhook that logs every notification and lists them, proving routing end to end. Slack, email or PagerDuty plug in next to it. |
| **Grafana** (`grafana/`) | Three dashboards (32 panels) generated by `build_dashboards.py` and provisioned read-only: changes go through git, not the UI. |
| **Blackbox exporter** | Outside-in HTTP checks: up or down, response time by phase (DNS, connect, TLS, server), certificate expiry. |
| **Node exporter** | Host CPU, memory, disk and network. |
| **Docker exporter** (`docker-exporter/`) | Per-container CPU, memory, network and restarts from the Docker Engine API, under cAdvisor's metric names. |
| **Runbooks** (`docs/runbooks.md`) | What each alert means, what to check first, how to fix the usual causes. |
| **CI** (`.github/workflows/validate.yml`, `scripts/validate.sh`) | Config syntax, rule checks, rule unit tests, Alertmanager config, every runbook link resolves, dashboards match their generator. |

### The alerts

| Alert | Fires when | Severity |
|---|---|---|
| TargetDown | a service can't be scraped for 1 minute | critical |
| ProbeFailed | an outside-in HTTP check fails for 2 minutes | critical |
| SlowResponse | a checked page averages over 2 s for 5 minutes | warning |
| TLSCertificateExpiringSoon | a certificate expires within 14 days | warning |
| HighErrorRate | over 5% of a service's requests are 5xx for 5 minutes, *with real traffic* | critical |
| HighLatencyP95 | p95 over 500 ms for 10 minutes, with real traffic | warning |
| DiskSpaceLow / DiskSpaceCritical | under 15% / 5% free | warning / critical |
| DiskWillFillIn24h | at the last 6 hours' rate the disk is full within a day, while it still has space | warning |
| HighCPU, MemoryPressure | over 90% for 15 / 10 minutes | warning |
| ContainerRestarting | a container restarted in the last 15 minutes | warning |
| Watchdog | always; if it stops arriving, the alert pipeline is broken | none |

## Running it

```bash
docker compose up -d
#   Grafana       http://localhost:3000   (admin / GRAFANA_ADMIN_PASSWORD, default change-me-locally)
#   Prometheus    http://localhost:9091
#   Alertmanager  http://localhost:9094
#   On-call page  http://localhost:9099

bash scripts/validate.sh          # everything CI checks, in containers
python grafana/build_dashboards.py  # after editing a dashboard
curl -X POST localhost:9091/-/reload  # after editing rules or targets
```

To watch Darviq-Buzz, start it first (`docker compose up -d` in that repo).
`node demo/traffic.mjs 15` sends 15 minutes of realistic browsing traffic so the dashboards
have something to show on a laptop: real requests through the real stack, nothing written into
the metrics directly.

## Proven live: an incident drill

With demo traffic running, `story-service` was stopped:

| Time | What happened |
|---|---|
| 15:18:01 | `docker compose stop story-service` |
| 15:19:31 | **TargetDown** firing in Alertmanager (1 minute `for:` plus scrape and evaluation interval) |
| 15:19:32 | Notification received by the on-call webhook |
| during | Home page p95 rose from about 0.5 s to 10 s: web-bff waits for story-service to time out |
| 15:27:33 | `docker compose start story-service` |
| 15:29:30 | **Resolved** notification received |

## What it found

Monitoring is only worth it if it tells you things you didn't know. In the first hour:

1. **A real bug in Darviq-Buzz.** The *Error ratio by service* panel showed post-service failing
   about 1% of requests. All of them were mistyped post URLs: a non-numeric id crashed the
   timestamp parser, so a typo became a **500** instead of a **404**. Fixed in Darviq-Buzz (three
   services shared the same helper).
2. **A mistake of my own.** The synthetic check for Buzz's gateway was failing from the start and
   briefly looked like a cascading failure during the drill. The gateway's health endpoint is
   `/api/health`; the check was pointed at `/health`. Fixed in `targets/probes/darviq-buzz.json`.
   Lesson recorded: when an alert fires from minute one, suspect the check before the system.
3. **A latency problem, still open.** HighLatencyP95 fires for Buzz's web front end: the home page's
   p95 is 0.5–0.7 s on a laptop, over the 500 ms objective, because it calls several services one
   after another. The fix (parallel calls) belongs in Darviq-Buzz.
4. **A flaw in Darviq-Buzz's own alerts.** Its `FeedFanoutStalled` and `NotificationConsumerStalled`
   rules fire whenever the site is quiet (no events consumed = "stalled"). They should only fire
   when messages are waiting in the queue and nothing consumes them.
5. **cAdvisor can't see containers on Docker Desktop** with the containerd image store (versions
   0.49 to 0.52 fail to map containers to their layers). Replaced by a 130-line exporter that asks
   the Docker Engine API directly and uses cAdvisor's metric names, so nothing else changed.

## Taking it to the cloud

The same configuration runs unchanged on a VM next to the workloads. For Kubernetes, the rules,
tests, dashboards and runbooks carry over as they are; Prometheus Operator (`PrometheusRule`,
`ServiceMonitor`) replaces the file-based targets, and kube-state-metrics adds pod-level alerts.
Managed alternatives keep the same rules: Amazon Managed Service for Prometheus with Amazon
Managed Grafana, or Grafana Cloud.

For fleets of AWS accounts, the companion project `aws-disk-monitoring` covers the other side:
Ansible over SSM (no SSH keys) pushing disk metrics into CloudWatch across many accounts, with
cross-account IAM roles deployed by StackSets.
